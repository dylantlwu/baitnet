## 重要

### I1. sandbox 下载失败时，要等约 2 分钟才降级，等待期间也没有提示可以跳过

用一个无法解析的域名模拟下载失败（DNS 失败，重试也不可能成功）：
```bash
BAITNET_REQUIRE_CHAIN=0 SANDBOX_ARTIFACT_URL=https://no-such-host.invalid/near-sandbox.tar.gz pnpm demo
```
```
  ! 下载 near-sandbox failed (attempt 1/8): fetch failed (cause: getaddrinfo ENOTFOUND no-such-host.invalid) — retrying in 2s
  ...
  ! 下载 near-sandbox failed (attempt 7/8): ... — retrying in 30s
  ✗ 本地 NEAR 链没能启动：fetch failed (cause: getaddrinfo ENOTFOUND no-such-host.invalid)
  ⚠ 降级：改用后端的内存版 registry（BAITNET_REGISTRY=memory）。
```
从启动到出现 `➜ 打开` 用了 **124s**，用 `--ci` 也是 124s。降级本身是成功的：`/alerts` 有 8 条，Dashboard 能正常显示（在补上 B1 的文件以后验证）。问题在于：

- 对于 DNS 解析失败（ENOTFOUND）或 HTTP 4xx 这类重试也不会好的错误，仍然要重试 8 次（2+4+8+16+30+30+30 秒）。
- 等待期间没有任何提示告诉用户"之后会自动降级"，也没说可以设 `NEAR_SANDBOX_BIN_PATH` 跳过下载。评委很可能以为程序卡住了，直接 Ctrl-C。
- README 只写了"resumable with retries"，没有说最坏要等多久。

建议：DNS 失败和 4xx 直接放弃，或者总等待时间控制在 30s 以内；第一次失败时就打印"N 次重试后会自动降级到内存模式"。

### I2. README 的介绍类章节全是 TODO 注释，渲染出来是空的

`## What it does`、`## Testnet deployment`、`## Architecture`、`## The agent's function-call key`、`## Known limitations`、`## Libraries, templates and AI-generated code` 这几节都只有 `<!-- TODO(...) -->`，开头也没有一段话的介绍。在 GitHub 上渲染出来就是一串空标题。评委（包括 Claude Code / Codex）读 README 时看不到项目在做什么，也看不到 HACKATHON 要求披露的 AI 生成代码说明。这不影响能不能跑起来，但会直接影响评审。

## 小问题

### M1. `--ci` 降级到内存模式时仍然显示 `✓ 全部通过`，exit 0
```bash
BAITNET_REQUIRE_CHAIN=0 SANDBOX_ARTIFACT_URL=http://127.0.0.1:9/x pnpm demo --ci   → exit 0
  ! 内存模式：跳过链上检查
✓ 全部通过
```
README 对 `--ci` 的说明是"检查警报在链上、vault.pay 被链上拒绝……"，但在降级情况下这些检查都被跳过了，结论还是"全部通过"。建议最后一行改成 `✓ 全部通过（内存模式，链上检查已跳过）`。GitHub CI 设置了 `REQUIRE_CHAIN=1`，所以不受影响。

### M2. 用 `kill -TERM` 正常退出后，pnpm 打印 "Command failed"
```
收到 SIGTERM，正在关闭所有子进程和 sandbox…
 ELIFECYCLE  Command failed with exit code 130.
```
清理本身是正常的（1s 内 3030/8787/5173 都释放了），但最后一行看起来像出错了。Ctrl-C 很可能也会这样。建议正常关闭时 exit 0，或者在 README 里说明这一行可以忽略。

### M3. vite 只监听 `[::1]:5173`，用 `127.0.0.1:5173` 访问会被拒绝
```
$ lsof -iTCP:5173 -sTCP:LISTEN   → node ... TCP [::1]:5173 (LISTEN)
$ curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:5173/   → 000（连接被拒绝）
```
README 写的是 `localhost`，所以按 README 操作没有问题；但如果评委的脚本或浏览器把 localhost 解析成 IPv4，就会访问失败。8787 监听的是 `*`，没有这个问题。可以考虑给 vite 加 `--host 127.0.0.1`，或者在 config 里设置 `server.host`。

### M4. `pnpm demo:export` 会覆盖已提交的 `apps/web/public/snapshot.json`
`snapshot.json` 在仓库文件列表里，每次 export 都会重写它（里面有时间戳和 tx hash），所以跑完 export 以后工作区就有改动了。如果这是有意为之（给 Vercel 用），建议在 README 里说明一下；如果不是，建议把这个文件加进 .gitignore，只提交 `snapshot.sample.json`。

### M5. `make test` 和 `pnpm test` 不等价
README 说 "`make demo`, `make demo-ci`, `make test` do the same"，但 Makefile 的 `test` 目标在装了 cargo 时还会跑 `contracts-test`（cargo test + near-workspaces），耗时和网络需求都比 `pnpm test` 大很多。建议 README 里注明这一点。

### M6. Node 版本要求的写法不一致
根目录 `package.json` 的 `engines` 是 `>=22`，README 写的是 "Node.js ≥ 22（near-api-js 7 / near-sandbox 要求 >=22.22）"，而 `near-sandbox` 实际声明的是 `>=22.22.2`。建议把 engines 改成 `>=22.22.2`，README 的表头也统一写这个版本。

### M7. 不在 TTY 下时，下载进度只打印一行 `0%`
```
  … 0.0/28.9 MB 0%
  ✓ sandbox 二进制已缓存: ...
```
`--ci` 或输出被重定向时只能看到一行 0%，然后直接显示完成。网络慢的时候会看起来像卡住了。建议非 TTY 时每 10% 或每 5 秒打印一行进度。
